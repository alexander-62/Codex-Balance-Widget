# Phase 01.1: Code Review Report

**Reviewed:** 2026-07-21T12:00:00Z

## Summary

Reviewed `probe_wham_usage.py` and `test_probe_wham_usage.py` against the commit that closed CR-01 (unredacted stdout print), CR-02 (`AttributeError` on malformed `rate_limit`/`additional_rate_limits` entries), and WR-01 (bare-exception fallback in `main()`). Those three specific defects are correctly fixed and covered by regression tests. No new crashes, injection vectors, or hardcoded secrets were found.

However, the fix for WR-01 introduces a residual gap in the module's core security invariant ("the access token is kept out of stdout, logs and any error message"): the new blanket `except Exception` handler in `main()` prints `str(exc)` unconditionally, without the `redaction_clean()` guard every other output path in this file applies. There is also a real (if narrow) correctness bug in `_remaining_percent()`'s truncation order, a missed defensive-typing gap in `_credits_text()`'s `unlimited` handling, and a case-sensitivity gap in `redact()`'s key matching that is inconsistent with the module's stated redaction guarantees. None of these are exploitable through any currently-reachable code path in this file, so none rise to Critical, but all four are genuine robustness/contract gaps that should be closed given this phase's explicit focus on redaction and malformed-payload hardening. A few test-quality gaps round out the findings.

## Warnings

### WR-01a: Blanket exception handler in `main()` bypasses the redaction-clean guarantee

**File:** `probe_wham_usage.py:422-426`
**Issue:** The bare `except Exception as exc: print(f"Непредвиденная ошибка: {exc}")` handler (added to fix WR-01) prints the raw exception text unconditionally. Every other output path in this module (the redacted stdout dump at line 386-392, and `write_fixture()` at line 351-357) is gated behind `redaction_clean()` before anything reaches stdout/disk. This handler is not. The module docstring makes an explicit, absolute claim: "The access token is kept out of stdout, logs and any error message, including under --debug." That claim is only true today because every currently-reachable exception happens to have a safe message (audited: all `ProbeError` call sites use static Russian strings or safe fields like HTTP status/content-type/timeout value; `URLError.reason` and the truncated Cloudflare HTML body don't include headers). But this is an invariant maintained by manual audit, not enforced by the code — any future exception whose `str()` embeds `access_token` (e.g., a stray f-string in new code, or a third-party library that echoes request headers on error) would print the secret directly to stdout, with no test able to catch it because `redaction_clean()` is simply never called on this path.
**Fix:** Apply the same guard used elsewhere, e.g.:
```python
except Exception as exc:
    message = f"Непредвиденная ошибка: {exc}"
    if not redaction_clean(message):
        message = "Непредвиденная ошибка (сообщение скрыто по соображениям безопасности)."
    print(message)
    if args.debug:
        traceback.print_exc()
    return 1
```

### WR-02: `load_tokens()` docstring promises "any failure" is converted to `ProbeError`, but `UnicodeDecodeError` is not caught

**File:** `probe_wham_usage.py:70-86`
**Issue:** The docstring states: "Raises ProbeError with a Russian diagnostic message on any failure (missing file, unreadable file, apikey-only auth_mode, missing/empty access_token)." The `try`/`except` only catches `FileNotFoundError` and `OSError` around `path.read_text(encoding="utf-8")`. If `auth.json` is not valid UTF-8 (corrupted file, wrong encoding), `read_text` raises `UnicodeDecodeError`, which is a `ValueError` subclass — **not** an `OSError` subclass — so it is not caught here. It propagates past `load_tokens()` and is only caught by `main()`'s generic `except Exception` (see WR-01a above), which contradicts both this function's documented contract and the module's "clean diagnostic only" design.
**Fix:**
```python
except (FileNotFoundError,) as exc:
    ...
except (OSError, UnicodeDecodeError) as exc:
    raise ProbeError(f"Не удалось прочитать файл auth.json ({path}).") from exc
```

### WR-03: `_remaining_percent()` truncates before subtracting, systematically overstating remaining quota

**File:** `probe_wham_usage.py:184-190`
**Issue:** `return str(100 - int(used))` truncates `used` toward zero *before* subtracting from 100. For any non-integer `used_percent`, this always rounds the displayed "remaining" value up. E.g. `used_percent = 99.9` → `int(99.9) = 99` → displayed remaining = `1`, even though the true remaining capacity is `0.1`. A user reading "1% remaining" when only 0.1% is actually left is materially misleading for a quota/rate-limit display — the whole point of this tool. `_reset_text()` and the rest of the module take care to use strict, correctness-first numeric handling; this function does not.
**Fix:**
```python
return str(int(100 - used))
```
(or `round(100 - used)` if fractional rounding rather than truncation is preferred — either is more correct than the current order of operations).

### WR-04: `_credits_text()`'s `unlimited` check has no type validation, unlike every other field extractor in this module

**File:** `probe_wham_usage.py:193-203`
**Issue:** `if credits_obj.get("unlimited"):` uses bare truthiness with no `isinstance` guard. Every sibling extractor (`_remaining_percent`, `_reset_text`) explicitly guards against wrong types (`isinstance(x, (int, float)) and not isinstance(x, bool)`) precisely because this module's stated design goal is defensive handling of malformed upstream payloads. Here, any truthy non-bool value for `unlimited` — including the string `"false"` (which is truthy in Python) — causes the function to report `"unlimited"` instead of falling through to the real numeric `balance`, silently producing an incorrect credits readout for a malformed/unexpected payload shape.
**Fix:**
```python
if credits_obj.get("unlimited") is True:
    return "unlimited"
```

### WR-05: `redact()`'s exact-match key list (`REDACT_KEYS`) is case-sensitive while the substring match is not, creating an inconsistent redaction guarantee

**File:** `probe_wham_usage.py:238-255`
**Issue:** Line 248: `key in REDACT_KEYS or "token" in key.lower()`. The `"token"` substring check is case-insensitive, but the `REDACT_KEYS` membership check (`user_id`, `account_id`, `email`, `chatgpt_user_id`, `session_id`, `individual_limit`) is an exact, case-sensitive match. If the upstream API ever returns any of these fields with different casing (e.g. `User_Id`, `AccountId`, `Session-Id` normalized differently across an API version), the value passes straight through `redact()` unredacted. Unlike a leaked email (still caught by the `"@"` substring check in `redaction_clean()`) or a JWT (caught by `"eyJ"`), a leaked `user_id`/`account_id`/`session_id`/`individual_limit` value has no shape that `redaction_clean()`'s narrow two-pattern post-check would ever catch — it would be written to the fixture file and printed to stdout undetected. Given this whole file's stated purpose is redacting exactly these fields, this is a real gap in the "belt" (key-based redaction), leaving only a "suspenders" (post-check) that doesn't cover this exact failure mode.
**Fix:** Normalize case before comparing:
```python
key_lower = key.lower() if isinstance(key, str) else None
if key_lower is not None and (key_lower in REDACT_KEYS or "token" in key_lower):
    result[key] = "<redacted>"
```
(and lower-case the `REDACT_KEYS` literals, which they already are).

## Info

### IN-01: Weak test assertion in `test_extract_fields_live_fixture`

**File:** `test_probe_wham_usage.py:152`
**Issue:** `self.assertIn("20", fields["weekly_reset_text"])` — checking for the substring `"20"` in a `%Y-%m-%d %H:%M` formatted string is a very weak assertion: it will pass for almost any date in the 2000s–2090s range (via the year), or coincidentally via day-of-month, hour, or minute containing "20". It does not actually verify that `reset_at=1784792381` was converted correctly.
**Fix:** Assert the exact expected string, e.g. compute it once with `datetime.fromtimestamp(1784792381).strftime("%Y-%m-%d %H:%M")` and compare with `assertEqual`.

### IN-02: No test exercises `main()`'s fixture-writing branch

**File:** `test_probe_wham_usage.py:384-419`
**Issue:** Both `TestMainErrorHandling` tests pass `["--no-fixture"]`, and no other test in the suite calls `main()` without that flag. The `write_fixture()` call inside `main()` (probe_wham_usage.py:411-414) — including the "Фикстура записана" success message — is therefore only covered indirectly (via the standalone `write_fixture()` unit tests), not through `main()`'s actual integration path.
**Fix:** Add a `TestMainErrorHandling`/`TestMainHappyPath` case that mocks `load_tokens`/`fetch_usage` with a clean payload, runs `main()` with a `--fixture` path pointing into a `tempfile.TemporaryDirectory()`, and asserts the file was written and the success message printed.

### IN-03: `auth_json_path()` has no dedicated unit test

**File:** `probe_wham_usage.py:64-67`, `test_probe_wham_usage.py` (whole file)
**Issue:** `auth_json_path()` (the `$CODEX_HOME` / `~/.codex` default-resolution logic) is never called from any test — all `load_tokens` tests construct the path directly and skip this function entirely.
**Fix:** Add a small test patching `os.environ` (with and without `CODEX_HOME` set) and asserting the resulting path, e.g. via `unittest.mock.patch.dict(os.environ, {...}, clear=True)`.
